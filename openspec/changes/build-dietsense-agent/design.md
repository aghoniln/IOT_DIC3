# Design

## Context

- 來源：根目錄 [`DESIGN.md`](../../../DESIGN.md)（八模組架構、Pseudocode、資料來源）已轉換為本變更；動機見 `proposal.md`，需求見 `specs/`。
- 現況：repo 只有提案文件（`myplan/`），尚無程式碼——屬 greenfield。
- 限制：課程要求保留 ①–⑧ 模組編號；提案期不得出現虛構結果；單人/小組、約 8 週實作；LLM API 成本需可控。

## Goals / Non-Goals

**Goals:**
- 任何熱量/營養素數字都可追溯到工具輸出與資料來源（可稽核）。
- 每個模組可獨立單元測試；分析與安全層 100% 確定性。
- 評估流程一鍵重現（固定模型版本、資料版本、隨機種子）。

**Non-Goals:**
- 不微調 LLM；不訓練自有 NER 模型（MVP 以 LLM + JSON schema 抽取）。
- 不做多租戶/高併發部署最佳化。

## Decisions

### D1. LLM 只做協調，數值由工具產生（vs. 讓 LLM 直接估算 / 微調營養 LLM）
- 理由：LLM 熱量估算 MAPE ~36%（Fridolfsson 2025）且無法溯源；微調後數值仍可能幻覺、更新資料需重訓。
- 作法：function calling + 工具白名單 + Response Guard（比對回應中的數字集合 ⊆ 本輪工具輸出集合）。
- 替代方案：Fine-tuned LLM（成本高、不可溯源）、純規則 KG（覆蓋率低、無法理解口語）。

### D2. 檢索優先序：臺灣 DB → 臺式料理卡 → USDA FDC
- 理由：臺灣在地食材以 TFDA 為權威；複合菜需「料理卡」拆解成分；USDA 補足包裝/西式食品。
- 料理卡以向量檢索（embedding）+ 名稱別名表（如「蚵仔煎 / 蚵煎」）雙路召回，再以規則排序。
- 替代方案：僅 USDA（臺式料理覆蓋不足）；網路爬蟲即時查（品質不可控）。

### D3. 不確定性以「區間傳遞」而非機率模型
- 每項 `[lo, pt, hi]` = 份量區間（份量表的 P10–P90）× 資料來源係數 × 信心擴張；日總和逐項相加（保守、易解釋）。
- 替代方案：Monte Carlo / Bayesian（較精確，但對 MVP 過重、使用者難理解）——列為 Future Work。

### D4. 追問策略：選擇「預期區間縮減最大」的單一問題，最多 2 輪
- 平衡 Q3-3 的「準確度 vs. 互動負擔」取捨；以每個未知欄位的 `hi − lo` 貢獻排序。
- 替代方案：一次問完所有欄位（負擔高）、從不追問（誤差大）。

### D5. 安全由 YAML 規則引擎決定，LLM 只負責措辭
- 規則版本化、有 rule ID、可單元測試；紅隊測試集驗證攔截率。
- 偵測語句採「關鍵詞 + LLM 分類器」雙保險，但最終決策由規則（任一命中即升級）。

### D6. 技術堆疊
- Python 3.11 + FastAPI；LLM：OpenAI 或 Gemini（抽象成 `LLMClient` 介面以便替換）；向量庫 Chroma（本地）；SQLite；pytest；Streamlit MVP UI。

## Risks / Trade-offs

- [臺式料理卡人工建置耗時] → 先做評估集中出現頻率最高的 ~300 道；每卡記錄來源與驗證者。
- [Response Guard 誤擋合法數字（如日期、份量 g）] → 只比對帶 kcal/g 營養單位的數字，白名單格式。
- [LLM 抽取錯誤（漏掉加料）] → JSON schema 驗證 + 回顯「我記錄為：…」讓使用者一鍵修正。
- [區間過寬失去實用性] → 監測平均區間寬度；以追問與預設份量縮小。
- [安全規則漏判或過度攔截] → 紅隊測試集（≥ 50 則）+ 誤報率指標；危險類別優先召回。
- [Mifflin-St Jeor 對特定族群失準] → 顯示限制；以 14 天體重趨勢校正實際 TDEE（Future Work）。
- [隱私] → 本地儲存、可匯出/刪除、評估資料去識別化。

## Migration Plan

新系統，無遷移。部署：本地 `uvicorn` + Streamlit；評估以 `eval/run.py` 產出報告。回滾：Git tag 每個里程碑。

## Open Questions

- LLM 供應商最終選擇（OpenAI vs Gemini）——由成本與繁中抽取品質小型試驗決定，不影響架構（D6 介面抽象）。
- 評估集的標註者是否能取得營養系同學協助——影響標註品質，不影響規格。
